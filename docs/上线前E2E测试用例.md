# 上线前 E2E 测试用例

## 1. 文档说明

本文档用于指导后续 Playwright E2E 脚本编写，覆盖 V1 上线必须验证的真实用户路径。它不是手工测试记录，而是自动化脚本设计清单：每条用例都说明登录态、造数方式、关键步骤、断言和建议落地文件。

现有前端测试说明见 `apps/web/test/README.md`。后续脚本建议继续放在 `apps/web/test` 下，并复用其中的登录态文件：

- `user_a`：发帖人、资源卖家、悬赏提问者
- `user_b`：买家、答主、评论者、举报者
- `user_c`：第二答主、普通旁观用户
- `admin`：后台管理员

## 1.1 与当前仓库现状的关系

- 当前 `apps/web/test` 下已有的 `smoke.e2e.spec.ts`、`authenticated.e2e.spec.ts`、`interaction-rules.e2e.spec.ts`、`admin.e2e.spec.ts` 只作为现状参考，不应反过来约束新的 E2E 设计。
- 如果现有 spec 过于综合、过于 API 驱动，后续可以直接拆分、迁移甚至替换，不需要为了保持目录和命名一致而保留旧结构。
- 本文中的“建议文件”按更适合长期维护的逻辑结构编排，默认使用 `apps/web/test/e2e/**` 作为目标布局，而不是继续贴着当前顶层 spec 展开。
- 当前 `auth-sessions.example.json` 只提供 `user_a`、`user_b`、`admin`。涉及 `user_c` 的场景需要在运行时通过真实 API 创建临时用户，或在私有 `auth-sessions.json` 中补齐。
- 最近后端已经把 posts 和 asset ledger 收敛成更稳定的边界。E2E 断言应优先对准：帖子读模型、钱包摘要、消息列表、购买/销售记录、后台审计结果，而不是假设旧的内部实现细节。

## 2. E2E 编写原则

- 优先覆盖 P0 核心闭环，不追求把所有边界都自动化。
- 自动化脚本应尽量通过真实前端页面完成操作，必要时用真实 API 做前置造数。
- 每条用例的测试数据使用唯一前缀，例如 `e2e-${Date.now()}`，避免和手工数据冲突。
- 断言不只看页面跳转，还要验证关键业务结果，例如隐藏内容是否解锁、钱包余额是否变化、后台列表是否出现记录。
- 资产类链路必须验证买家、卖家、流水、交易状态至少两个视角。
- 管理员能力只做上线必要冒烟，不把后台所有筛选组合都做成 E2E。
- 已有综合 spec 中凡是大量通过 API 完成主流程的，后续补强应优先把“用户真正点击的关键动作”迁回页面，例如发布、购买、采纳、后台下架，而把 API 退回为前置造数或结果校验手段。

## 2.1 当前自动化覆盖与缺口

当前 `apps/web/test` 已经覆盖：

- 游客访问和鉴权跳转冒烟
- 用户页访问、资源购买、悬赏采纳、消息、举报、申诉的综合 API 驱动流程
- 管理后台页面和权限冒烟

当前仍然缺的，是更贴近真实操作的页面级闭环：

- 发帖页表单输入和校验
- 资源帖页面购买按钮、解锁状态、重复购买拦截
- 悬赏帖页面回答提交、采纳按钮、回答可见性
- 后台帖子下架、后台审计列表与前台状态联动

## 3. 全局前置数据

| 数据 | 用途 | 建议准备方式 |
| ---- | ---- | ------------ |
| 用户 A | 发帖人、资源卖家、悬赏提问者 | 使用 `auth-sessions.json` 中 `user_a` |
| 用户 B | 买家、答主、评论者、举报者 | 使用 `auth-sessions.json` 中 `user_b` |
| 用户 C | 第二答主、普通旁观用户 | 优先使用 `auth-sessions.json` 中 `user_c`；如缺少，则在测试开始时通过 API 注册临时用户 |
| 管理员 | 后台管理、审计、下架 | 使用 `auth-sessions.json` 中 `admin` |
| 分类和标签 | 发帖、筛选、列表展示 | 测试环境 seed 或 API 前置检查 |
| 初始金币 | 资源购买、悬赏发布 | 注册赠送或后台加币前置 |
| 测试资源帖 | 资源购买链路 | 用用户 A 通过页面或 API 创建 |
| 测试悬赏帖 | 悬赏采纳链路 | 用用户 A 通过页面或 API 创建 |

## 3.1 统一前置检查建议

- 在每个需要登录态的 spec 开始时，显式检查 `baseURL` 和 session 文件是否存在，缺少时 `test.skip(...)` 并输出明确原因。
- 在每个资产链路 spec 内记录操作前后的钱包摘要：`availableCoins`、`frozenCoins`、`totalCoins`。
- 涉及唯一标题的帖子造数统一使用 `e2e-${Date.now()}-${testInfo.workerIndex}` 前缀，避免首页搜索和后台列表互相串数据。
- 若某条链路依赖分类和标签，先通过真实 API 检查是否存在 seed 数据；缺失时直接跳过，而不是在 UI 上盲点失败。

## 8. 脚本实现建议

- 推荐把新脚本收敛到 `apps/web/test/e2e/**`，按领域拆分，而不是继续把所有场景堆在顶层综合 spec 中。
- 现有 `smoke.e2e.spec.ts`、`authenticated.e2e.spec.ts`、`interaction-rules.e2e.spec.ts`、`admin.e2e.spec.ts` 可以逐步被拆分后的新 spec 替代，不要求兼容旧结构。
- 需要登录的测试先读取 `test/testdata/auth-sessions.json`，若缺少用户则跳过对应用例并输出清晰原因。
- 涉及 `user_c` 的场景，优先通过 helper 在运行时创建临时用户；只有长期稳定场景才要求固定 session。
- 造数优先用真实 API 创建帖子、资源帖、悬赏帖，页面测试只覆盖用户真正会操作的关键路径。
- 资产相关测试执行后要记录购买前后、发布前后、采纳前后余额，并在钱包摘要、钱包流水或后台审计中二次确认。
- 对于悬赏可见性这类容易“前端看起来对了、接口其实没收口”的场景，建议同时校验页面文本和接口读模型字段，例如 `canViewContent`、`maskedSummary`。
- 每个 spec 内部使用唯一标题前缀，格式建议：`e2e-${Date.now()}-${testInfo.workerIndex}`。
- 涉及后台下架、申诉处理、退款的用例要放在独立数据上，避免影响其他测试。
- 如果某个 V1 功能决定延期，E2E 应改为验证入口隐藏或显示“开发中”，而不是保留失败脚本。

## 9. 推荐拆分方式

- 第一批可以直接建立新的 `test/e2e/**` 结构，把资源购买、悬赏闭环、消息中心拆成单职责 spec，而不是继续扩展现有综合文件。
- 第二批再把后台相关场景细化为权限冒烟、帖子下架、钱包/交易审计三条独立 spec。
- 第三批再补页面级发帖表单、列表搜索、移动端和错误页场景；旧 spec 可在新结构稳定后下线或只保留极轻的冒烟职责。
