# 上线前 E2E 测试用例

## 1. 文档说明

本文档用于指导后续 Playwright E2E 脚本编写，覆盖 V1 上线必须验证的真实用户路径。它不是手工测试记录，而是自动化脚本设计清单：每条用例都说明登录态、造数方式、关键步骤、断言和建议落地文件。

现有前端测试说明见 `apps/web/test/README.md`。后续脚本建议继续放在 `apps/web/test` 下，并复用其中的登录态文件：

- `user_a`：发帖人、资源卖家、悬赏提问者
- `user_b`：买家、答主、评论者、举报者
- `user_c`：第二答主、普通旁观用户
- `admin`：后台管理员

## 2. E2E 编写原则

- 优先覆盖 P0 核心闭环，不追求把所有边界都自动化。
- 自动化脚本应尽量通过真实前端页面完成操作，必要时用真实 API 做前置造数。
- 每条用例的测试数据使用唯一前缀，例如 `e2e-${Date.now()}`，避免和手工数据冲突。
- 断言不只看页面跳转，还要验证关键业务结果，例如隐藏内容是否解锁、钱包余额是否变化、后台列表是否出现记录。
- 资产类链路必须验证买家、卖家、流水、交易状态至少两个视角。
- 管理员能力只做上线必要冒烟，不把后台所有筛选组合都做成 E2E。

## 3. 全局前置数据

| 数据 | 用途 | 建议准备方式 |
| ---- | ---- | ------------ |
| 用户 A | 发帖人、资源卖家、悬赏提问者 | 使用 `auth-sessions.json` 中 `user_a` |
| 用户 B | 买家、答主、评论者、举报者 | 使用 `auth-sessions.json` 中 `user_b` |
| 用户 C | 第二答主、普通旁观用户 | 使用 `auth-sessions.json` 中 `user_c`，缺少时通过 API 注册临时用户 |
| 管理员 | 后台管理、审计、下架 | 使用 `auth-sessions.json` 中 `admin` |
| 分类和标签 | 发帖、筛选、列表展示 | 测试环境 seed 或 API 前置检查 |
| 初始金币 | 资源购买、悬赏发布 | 注册赠送或后台加币前置 |
| 测试资源帖 | 资源购买链路 | 用用户 A 通过页面或 API 创建 |
| 测试悬赏帖 | 悬赏采纳链路 | 用用户 A 通过页面或 API 创建 |

## 8. 脚本实现建议

- `anonymous-access.spec.ts` 不依赖登录态，缺少 session 文件时仍可跑。
- 需要登录的测试先读取 `test/testdata/auth-sessions.json`，若缺少用户则跳过对应用例并输出清晰原因。
- 造数优先用真实 API 创建帖子、资源帖、悬赏帖，页面测试只覆盖用户真正会操作的关键路径。
- 资产相关测试执行后要记录购买前后余额，并在钱包流水或后台审计中二次确认。
- 每个 spec 内部使用唯一标题前缀，格式建议：`e2e-${Date.now()}-${testInfo.workerIndex}`。
- 涉及后台下架、申诉处理、退款的用例要放在独立数据上，避免影响其他测试。
- 如果某个 V1 功能决定延期，E2E 应改为验证入口隐藏或显示“开发中”，而不是保留失败脚本。
